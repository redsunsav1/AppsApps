# PartnerBuild — Операционный runbook

Что нужно сделать руками один раз, и что делать, когда что-то сломалось.

---

## Чек-лист перед запуском партнёров

- [ ] `BOT_TOKEN` задан (иначе валидация initData отключена — критическая дыра)
- [ ] `ADMIN_TELEGRAM_ID` задан — без него алерты никуда не приходят
- [ ] `ADMIN_PIN` задан (второй фактор админки)
- [ ] `ADMIN_SECRET` — длинная случайная строка, не дефолт
- [ ] `ALLOW_CLEAR_USERS=false`, `ENABLE_TEST_NOTIFY=false`, `SEED_DEMO_DATA=false`
- [ ] `MAX_TRUST_INIT_DATA` НЕ установлен (это dev-режим без валидации)
- [ ] SMTP настроен и тестовое письмо дошло (`SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_SALES`)
- [ ] Бэкапы включены и проверено восстановление (см. ниже)
- [ ] Внешний мониторинг настроен на `/api/ping` (см. ниже)

## Бэкапы БД

Amvera делает автоматические бэкапы, но бэкап без проверенного восстановления — не бэкап.

**Раз в месяц — пробное восстановление:**
1. В панели Amvera скачать последний бэкап (или через `pg_dump`, если есть прямой доступ):
   ```bash
   pg_dump "$DATABASE_URL" -Fc -f partnerbuild_$(date +%Y%m%d).dump
   ```
2. Восстановить в пустую локальную/тестовую базу:
   ```bash
   pg_restore -d postgresql://localhost/partnerbuild_test partnerbuild_YYYYMMDD.dump
   ```
3. Проверить: `SELECT count(*) FROM users;`, `SELECT count(*) FROM bookings;` — числа совпадают с продом.
4. Зафиксировать дату проверки (хоть в этом файле).

**Retention:** держать минимум 30 дней. Скачанный раз в неделю дамп на отдельном диске — дешёвая страховка от проблем на стороне хостинга.

## Внешний мониторинг

`GET /api/ping` возвращает `200` когда всё живо и `503` когда БД недоступна, плюс детали: статус интеграций, аптайм, время последнего синка фида.

**Настройка UptimeRobot (5 минут, бесплатно):**
1. uptimerobot.com → Add Monitor → HTTP(s).
2. URL: `https://<домен>/api/ping`, интервал 5 минут.
3. Alert contacts: email + Telegram (у UptimeRobot есть интеграция с Telegram-ботом).

Алерты, которые приложение шлёт само (в `ADMIN_TELEGRAM_ID` и, при включённом MAX, в `ADMIN_MAX_ID`):
- фид не синхронизируется 3 раза подряд (~15 минут);
- фид «усох» — вернул меньше половины квартир (синк остановлен, данные целы);
- квартира продана застройщиком, но у нас на неё активная бронь;
- AmoCRM не принял лид (не чаще раза в час; лид досоздаётся автоматически каждые 15 минут);
- письмо с документами не отправилось / SMTP не настроен.

## Аудит-лог

Все ключевые действия пишутся в таблицу `audit_log`: кто (риелтор/админ), что (`booking.create`, `booking.passport_upload`, `booking.complete`, `booking.revoke`, `application.approve`, `user.delete`, `settings.change`, …), с чем и когда.

Просмотр: `POST /api/admin/audit` с телом `{ "initData": "...", "action": "booking.", "limit": 100 }` (фильтры: `action` — префикс, `actorId`, `from`, `to`, `limit`, `offset`). Таблица append-only — приложение её никогда не чистит.

При споре «бронь пропала»: `action: "booking."` + период — видно всю историю по сделке.

## PIN админки

Второй фактор поверх Telegram-аутентификации. Включение: задать `ADMIN_PIN` в окружении и перезапустить. После этого админка запросит PIN (хранится в sessionStorage до закрытия приложения, уходит в заголовке `x-admin-pin`). Перебор ограничен: 10 попыток проверки за 15 минут, неудачные попытки пишутся в аудит-лог (`admin.pin_failed`).

Смена PIN — смена переменной + рестарт. Забыли PIN — он в панели переменных окружения Amvera.

## Инциденты

**Сервер не отвечает (`/api/ping` timeout):** панель Amvera → рестарт приложения → смотреть логи старта (`Server running on port`). Если падает на старте — чаще всего БД (`Fatal: could not init DB`).

**БД недоступна (`/api/ping` → 503):** статус БД в Amvera; проверить `DATABASE_URL`; после восстановления сервер сам переподключится (pool). Бронирования в этот период не создавались — потери данных нет, потеря только доступности.

**Шахматка пустая/неполная:** проверить алерты в Telegram. Если сработала защита фида — фид застройщика вернул мусор, данные в базе целы, синк восстановится сам. Если уменьшение реальное (корпус выведен), временно `FEED_SHRINK_GUARD=off` + рестарт + ресинк проекта из админки, затем вернуть `on`.

**Лиды не появляются в AmoCRM:** `GET /api/ping` → `amocrm: configured`? Токен AmoCRM долгоживущий, но отзываемый — проверить в AmoCRM. Несозданные лиды досоздаются кроном каждые 15 минут после восстановления доступа; вручную ничего переносить не надо.

**Паспорт не дошёл на почту:** алерт укажет причину. Файл также прикреплён к лиду AmoCRM (`AMOCRM_ATTACH_FILES=true`). В крайнем случае — попросить риелтора отправить повторно (кнопка активна, пока `passport_sent` не выставлен).

**Потеря данных:** восстановление из последнего бэкапа (см. выше) в НОВУЮ базу, переключить `DATABASE_URL`, рестарт. Старую базу не удалять до выяснения причин.
